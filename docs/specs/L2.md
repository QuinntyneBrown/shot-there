# L2 - Detailed Requirements

Conventions used throughout:

- Viewport sizes: XS is narrower than 576px, SM is 576px to 767px, MD is 768px to 991px, LG is 992px to 1199px, XL is 1200px and wider.
- "Published" means a location or guide whose status is `published`; everything else is `draft`.
- "The owner" means the single authenticated administrator account.
- All-in cost for a standard 2-hour shoot = (hourly rate × max(2, minimum booking hours)) + sum of mandatory fees, rounded to the nearest cent, shown in Canadian dollars.
- Scoring rubric: six categories, Value, Light, Space, Gear, Logistics, Condition, each an integer from 1 to 5. Overall score = arithmetic mean of the six, rounded to one decimal place.
- "Stale" means a last-verified date more than 183 days before today.

---

## L2-001: Only published locations are visible to visitors
**Traces to:** L1-001

The public site must expose only locations whose status is `published`. Draft locations must not appear in lists, maps, comparisons, guides, rain-backup lists, sitemaps, or structured data, and their pages must not be reachable by URL.

**Acceptance Criteria:**
1. Given a studio in `draft` status, when a visitor requests its page URL, then the server responds with HTTP 404 and the site's not-found page.
2. Given one published studio and one draft studio, when a visitor opens the studio list, then only the published studio is listed.
3. Given a draft outdoor spot, when a visitor requests the sitemap, then the draft spot's URL is absent.
4. Given a draft studio, when the public API is asked for the studio list, then the draft studio is absent from the response.

---

## L2-002: Publishing requires the standard data set
**Traces to:** L1-001

A location must not be publishable until every field in its standard data set is present. For studios the standard set is: name, neighbourhood, address or cross streets, booking link, hourly rate, minimum booking hours, price last-verified date, usable shooting space, ceiling height, window direction, natural light by time of day, power, cyc wall presence, at least one standard test shot image, at least one gallery image, all six rubric scores, verdict text, and disclosure. For outdoor spots the standard set is: name, neighbourhood, coordinates, how to get there, best light by time of day, best light by season, at least one sample shot image, permit status, permit source link, permit last-verified date, and at least one best use.

**Acceptance Criteria:**
1. Given a draft studio missing its ceiling height, when the owner attempts to publish it, then publishing is refused and the response lists `ceilingHeight` as a missing field.
2. Given a draft studio with every standard field present, when the owner publishes it, then its status becomes `published` and its page is reachable.
3. Given a draft outdoor spot missing its permit source link, when the owner attempts to publish it, then publishing is refused and the response lists `permitSourceUrl` as a missing field.
4. Given a published studio, when the owner clears a standard field and saves, then the save is refused with a validation message naming the field, and the studio stays published with its previous value.

## L2-003: Studio basics
**Traces to:** L1-002

Each studio page must show the studio's name, neighbourhood, address or cross streets, and a link to the studio's own booking page that opens in a new tab with `rel="noopener"`.

**Acceptance Criteria:**
1. Given a published studio, when a visitor opens its page, then the name is the page's level-one heading and the neighbourhood and address or cross streets are shown beneath it.
2. Given a published studio with a booking link, when a visitor activates the booking link, then the studio's booking page opens in a new tab and the link element carries `rel="noopener"`.
3. Given a published studio, when the page is viewed at XS, then the basics block is a single column and no element overflows the viewport width.

---

## L2-004: Studio pricing and all-in cost
**Traces to:** L1-002

Each studio page must show the hourly rate, minimum booking hours, each extra fee with whether it is mandatory or optional, and a calculated all-in cost for a standard 2-hour shoot, computed by the server from the stored values.

**Acceptance Criteria:**
1. Given a studio with hourly rate $60, minimum booking 1 hour, and no fees, when a visitor views its page, then the all-in cost shows $120.00.
2. Given a studio with hourly rate $60, minimum booking 3 hours, and no fees, when a visitor views its page, then the all-in cost shows $180.00.
3. Given a studio with hourly rate $60, minimum booking 2 hours, a mandatory cleaning fee of $25, and an optional strobe rental of $40, when a visitor views its page, then the all-in cost shows $145.00 and the strobe rental is listed as optional and excluded.
4. Given a studio with hourly rate $45.50 and minimum booking 2 hours, when a visitor views its page, then the all-in cost shows $91.00 formatted as Canadian dollars with two decimals.
5. Given a published studio, when the public API returns it, then the response includes `allInCost2h` already calculated by the server.

## L2-005: Price last-verified date
**Traces to:** L1-002

The pricing block must show the date the pricing was last verified in a long date format and must carry a stale warning when that date is stale.

**Acceptance Criteria:**
1. Given a studio whose price was verified 30 days ago, when a visitor views its page, then the pricing block shows "Prices verified" followed by the date, and no stale warning is shown.
2. Given a studio whose price was verified 200 days ago, when a visitor views its page, then the pricing block shows a visible warning that pricing may be out of date, and the warning is announced to assistive technology as a status region.
3. Given a studio whose price was verified exactly 183 days ago, when a visitor views its page, then no stale warning is shown.

## L2-006: Measured specifications
**Traces to:** L1-002

Each studio page must show the measured specifications: usable shooting space (metres and feet), ceiling height (metres and feet), window direction, natural light by time of day (morning, midday, afternoon, evening, each rated none, low, medium, or strong), power (number and type of outlets, and whether 20A circuits are available), cyc wall presence and condition, and available backdrops.

**Acceptance Criteria:**
1. Given a studio with usable space 6.1 m × 4.3 m, when a visitor views its page, then the specifications show "6.1 m × 4.3 m (20 ft × 14 ft)".
2. Given a studio with no cyc wall, when a visitor views its page, then the cyc wall row shows "No" and no condition is shown.
3. Given a studio with a cyc wall in condition "scuffed", when a visitor views its page, then the cyc wall row shows "Yes" and the condition "scuffed".
4. Given any published studio, when a visitor views its page, then the natural light row shows all four times of day with a rating for each, in a layout that stacks to one column at XS and shows as a four-column row at MD and above.

## L2-022: Studio filters
**Traces to:** L1-004

The studio list must offer filters for all-in cost range (minimum and maximum), neighbourhood (multi-select), natural light (at least medium at any time of day), cyc wall (yes), usable space (minimum square metres), included gear (multi-select from lights, modifiers, stands, backdrops), and parking (on-site, street, none). Filters combine with AND; multi-select values within a filter combine with OR.

**Acceptance Criteria:**
1. Given studios with all-in costs $90, $120, and $200, when a visitor sets the range to $100 to $150, then only the $120 studio is listed.
2. Given studios in Leslieville and Junction, when a visitor selects both neighbourhoods, then both studios are listed.
3. Given a visitor selects "Cyc wall" and "Parking: on-site", when the list updates, then only studios with both are shown.
4. Given a filter combination that matches nothing, when the list updates, then an empty state explains that no studios match and offers a "Clear filters" action that resets all filters.
5. Given the list at XS, when a visitor opens filters, then they appear in a full-height dialog with an "Apply" action and a close control; at LG and above the filters are shown in a sidebar beside the list.
6. Given the list and an active filter set, when the visitor views the filters control, then it shows the count of active filters.

## L2-023: Studio sort
**Traces to:** L1-004

The studio list must sort by all-in cost (ascending), overall score (descending), or most recent review (descending).

**Acceptance Criteria:**

2. Given studios with overall scores 3.8, 4.5, and 4.5, when a visitor sorts by overall score, then both 4.5 studios appear before 3.8 and ties are ordered by review date descending.

## L2-024: Outdoor spot list and filters
**Traces to:** L1-004

**Acceptance Criteria:**

2. Given a visitor filters by use case "family" and permit "no permit needed", when the list updates, then only spots tagged family whose portrait-shoot permit status is "Not required" are listed.
3. Given a filter that matches nothing, when the list updates, then an empty state with "Clear filters" is shown.
4. Given the spot list at XS, when viewed, then cards are one column with no horizontal scroll.

## L2-025: Filter and sort state in the URL
**Traces to:** L1-004

The current filters, sort, and list type must be encoded in the URL query string so that the same URL reproduces the same view, and browser back and forward must restore previous views.

**Acceptance Criteria:**
1. Given a visitor sets neighbourhood to Leslieville and sort to all-in cost, when they copy the URL and open it in a new session, then the list shows the same filters and sort applied.
2. Given a visitor applies a filter and then presses browser Back, when the page updates, then the previous filter state is restored.
3. Given a URL with an unknown filter value, when the list loads, then the unknown value is ignored, the remaining valid filters apply, and no error is shown.
4. Given a URL with a cost minimum greater than the maximum, when the list loads, then the range is treated as unset and the filter control shows no range.

## L2-030: Selecting studios to compare

**Acceptance Criteria:**

4. Given two studios selected, when the visitor activates "Compare" in the bar, then the comparison page opens with those two studios.
5. Given a selection, when the visitor reloads the page, then the selection persists in the browser.
6. Given the compare bar at XS, when shown, then it is fixed to the bottom of the viewport, respects the bottom safe-area inset, and does not overlap page content when scrolled to the end.

## L2-080: CSRF, headers and transport
**Traces to:** L1-019

State-changing requests must be protected against cross-site request forgery, all responses must carry security headers, and all traffic must be over HTTPS.

**Acceptance Criteria:**
1. Given a state-changing administration request from a different origin without the anti-forgery token, when received, then the server responds HTTP 403.
2. Given any response, when inspected, then it carries a `Content-Security-Policy` that allows scripts only from the site's own origin and frames only from `youtube-nocookie.com` and the map provider, plus `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and `Strict-Transport-Security` with a max age of at least one year.
3. Given a request over plain HTTP, when received in production, then the server responds HTTP 301 to the HTTPS URL.
4. Given the compiled client bundle, when searched, then it contains no API keys, database credentials, or session secrets; the map provider key, if any, is domain-restricted.

## L2-081: Upload safety
**Traces to:** L1-019

Uploaded files must be stored outside the web root or in object storage under server-generated names, served with fixed content types, and never executed.

**Acceptance Criteria:**
1. Given an uploaded image named `../../etc/passwd.jpg`, when stored, then it is saved under a server-generated name and the original name is used only as metadata.
2. Given an uploaded image, when served, then the response `Content-Type` is derived from the server's inspection, not from the original filename.
3. Given an upload endpoint, when called without a session, then the response is HTTP 401 and nothing is stored.

## L2-082: Dependency and secret hygiene
**Traces to:** L1-019

The build must fail on known high-severity vulnerabilities in dependencies, and secrets must be supplied through environment configuration.

**Acceptance Criteria:**
1. Given the continuous integration pipeline, when a dependency with a known high or critical vulnerability is present, then the build fails.
2. Given the repository, when scanned for secrets, then no credentials are committed; configuration is read from environment variables with documented names.

## L2-083: Error pages
**Traces to:** L1-020

The site must show a branded not-found page for unknown URLs and a branded error page for server failures, each with navigation back to the home page, and must return the matching HTTP status.

**Acceptance Criteria:**
1. Given a request to a URL that matches no route, when received, then the response is HTTP 404 with the not-found page containing a link to the home page and the studio list.
2. Given an unhandled server error while rendering a page, when it occurs, then the response is HTTP 500 with the error page and no stack trace or internal detail in the body.
3. Given either error page at XS, when viewed, then it is readable with no horizontal scroll.

## L2-084: Health check
**Traces to:** L1-020

The backend must expose an unauthenticated health endpoint reporting its own status and the data store's reachability.

**Acceptance Criteria:**
1. Given the backend and data store are running, when `/api/health` is requested, then the response is HTTP 200 with `{"status":"ok"}`.
2. Given the data store is unreachable, when `/api/health` is requested, then the response is HTTP 503 with `{"status":"degraded"}` and no connection details.
3. Given the health endpoint, when requested, then it responds within 500 ms.

## L2-085: Structured logging
**Traces to:** L1-020

The backend must emit one structured log line per request and per error, with a correlation ID, and must never log secrets, session tokens, passwords, or subscriber emails in full.

**Acceptance Criteria:**
1. Given any request, when it completes, then a JSON log line is emitted containing method, path, status, duration in milliseconds, and a correlation ID that is also returned in a response header.
2. Given a sign-in request, when logged, then the password is absent from the log line.
3. Given an email signup, when logged, then the email is masked to its first character and domain.
4. Given an unhandled error, when logged, then the line includes the correlation ID, error name, and stack, at level `error`.

## L2-086: Graceful media degradation
**Traces to:** L1-020

Pages must render correctly when an image, map tile service, or video poster fails to load.

**Acceptance Criteria:**
1. Given a gallery image URL that returns HTTP 404, when the page renders, then a placeholder with the image's alt text is shown in its slot and layout does not shift.
2. Given the map tile service is unreachable, when a spot page renders, then the map area shows a message with the coordinates and a link to open the location in an external map, and the rest of the page is unaffected.
3. Given a video poster that fails to load, when the page renders, then the "Play episode" control remains usable.

## L2-087: Static and cached delivery
**Traces to:** L1-021

Public pages must be deliverable as statically generated or incrementally regenerated output behind a CDN, with the dynamic backend needed only for administration, signup, and regeneration.

**Acceptance Criteria:**
1. Given the production build, when run, then every public page that existed at build time is emitted as static HTML or is served from the CDN cache after first render, and a report lists the generated routes.
2. Given the backend is stopped, when a visitor requests a cached public page through the CDN, then the page is still served.
3. Given the owner publishes a change, when regeneration runs, then only the affected pages, their lists, the map data, and the sitemap are regenerated.
4. Given MVP traffic of 10,000 page views per day, when hosting usage is reviewed, then the public site runs within the CDN and hosting provider's free or lowest tier.
