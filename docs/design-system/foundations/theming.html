Foundation

Theming

ShotThere ships a light theme and a dark theme from one set of semantic tokens. A theme changes what the roles resolve to; components never know which theme they are in, and the photos, map tiles and episode posters never change at all.

Overview

Light is a white canvas with near-black ink and one accent red that means "selected" or "you are here". Dark is a warm near-black canvas with light stone ink and a lighter, softer accent red. Both are first-class: every contrast pair is checked in both, every component page shows both, and every one of the 143 mocks renders in both (t or ?theme=dark).

  • One source. tokens/tokens.css holds light on :root and dark in two identical blocks. tokens/tokens.json is generated from it for other platforms.
  • Themes override semantic tokens only. Primitives (--palette-*) never change; component tokens (--btn-*, --alert-*) alias semantic tokens and follow automatically.
  • The operating system decides by default. With no choice made, ShotThere follows prefers-color-scheme. A page or a subtree can force either theme with data-theme.
  • Content keeps its colours. Studio and spot photos, test shots, map tiles and episode posters are content. No theme dims, inverts or filters them (see Photos and map tiles).

How themes apply

data-theme="dark" on one elementThat subtree is darkThe dark block matches any element, so custom properties cascade from it (the side-by-side examples on these pages use this)

Each theme also sets color-scheme: light or color-scheme: dark, so native controls follow without extra styles: the date picker for "Prices last verified", number fields for the hourly rate, scrollbars on the comparison table and email autofill in the signup form. Set the attribute before first paint to avoid a flash of the wrong theme:

<html lang="en-CA">
<script>
  // Before any stylesheet paints: apply a saved choice, else follow the operating system.
  try { var t = localStorage.getItem('theme'); if (t === 'dark' || t === 'light') document.documentElement.dataset.theme = t; } catch (e) {}
</script>

Store a choice only when someone makes one; removing the attribute hands control back to the operating system. The public site has no theme switch in its header today, so visitors get their system setting. The mocks and these docs also accept ?theme=dark or ?theme=light and the t key; those are review conveniences, not product features.

Themes and breakpoints are independent. The responsive layout tokens (--layout-columns, --layout-gutter, --layout-margin, --layout-topbar-height, display sizes) change by viewport and are identical in both themes.

Token tiers

A value appears once as a primitive, gets meaning as a semantic token, and is scoped to one component as a component token. Each tier reads only from the tier above it.

TierPrefixShotThere exampleWho reads itThemes change it?
1 · Primitive--palette-*, --font-*, --line-height-*, --letter-spacing-*--palette-pepper-600 (accent red), --palette-pepper-300, --palette-stone-950 (ink)Semantic tokens onlyNever
2 · Semantic--color-*, --text-*, --space-*, --radius-*, --shadow-*, --duration-*, --ease-*, --z-*, --layout-*, --target-*, --control-height-*, --icon-*--color-accent: var(--palette-pepper-600) in light, var(--palette-pepper-300) in darkComponents and pagesYes: colours, shadows and color-scheme

So "Book on the studio's site" fills with --btn-bg → --color-action → --palette-stone-950 in light and --palette-stone-100 in dark, and a studio marker on the map reads the same --color-action. Changing the accent hue touches primitives; changing what "action" means touches the semantic tier; changing how the compare toggle looks when pressed touches the component tier.

Because markers change with the theme but tiles don't, every marker carries the surface-coloured halo: it separates an ink square from a dark park and a light stone square from a pale road. --color-bg-scrim exists for text set directly over a photo; no ShotThere component does that today (the play label sits on its own solid pill), so keep it that way rather than reaching for the scrim.

Contrast and forced colours

Two more preferences adjust the active theme rather than replacing it.

Media queryWhat changes
prefers-contrast: moreDefault borders take --color-border-strong, so summary-panel, stat-tile, editor-section and table edges reach 3:1; muted text becomes default ink and subtle text becomes muted. Applies in both themes.
forced-colors: active (Windows High Contrast)The focus ring becomes Highlight and borders CanvasText. Buttons, fields, chips, badges, tags and filter triggers draw a system-colour border so their edges stay visible; the primary button uses Highlight/HighlightText; pressed segments in the Map/List and Both/Studios/Spots toggles are underlined because colour alone disappears; dialogs, sheets and toasts gain a 1px CanvasText edge.

Icons draw with currentColor and need nothing extra. Never use forced-color-adjust: none on content such as photos or map tiles; it is reserved for the controls above, which then supply system colours themselves.

Adding a theme

A new theme, for example a higher-contrast variant, is another [data-theme="<name>"] block that overrides semantic colour tokens and nothing else.

  1. Add any new raw colours as primitives in :root (--palette-*).
  2. Write [data-theme="<name>"] { … } overriding only --color-*, --shadow-* and color-scheme. Never override spacing, type, radius, motion or layout in a theme, and never component tokens.
  3. Override every role the light theme defines, not just the ones that look wrong: a missed role silently falls back to light.
  4. Run check_contrast.py (in .claude/skills/extracting-design-systems/scripts/); it picks up every [data-theme] block by itself. Make every pair in contrast-pairs.json pass with margin (aim for 4.8:1 on body text and 3.3:1 on edges and pips).
  5. Keep the accent red meaning "selected" and the ink button meaning "the one action on this screen". A theme changes colours, not meanings.
  6. Check the markers on a real tile set: the halo must still separate them from the map.
  7. Regenerate tokens.json and check the mocks with ?theme=<name> where the mock script supports it.
[data-theme="high-contrast"] {
  --color-fg-muted: var(--palette-stone-950);
  --color-fg-subtle: var(--palette-stone-800);
  --color-border-default: var(--palette-stone-700);
  --color-border-strong: var(--palette-stone-950);
  --color-accent: var(--palette-pepper-700);
  --color-fg-accent: var(--palette-pepper-700);
  --color-focus-ring: var(--palette-pepper-800);
  /* …every other --color-* role… */
  color-scheme: light;
}

Consuming tokens.json

tokens/tokens.json follows the W3C Design Tokens Community Group (DTCG) format and is regenerated from tokens.css by tokens_to_json.py (in the same scripts folder); never edit it by hand.

  • Groups follow the names. --color-accent-subtle-hover lives at color.accent.subtle.hover; --duration-loop-fast at duration.loop.fast.
  • Each token has $type and $value: color, dimension, duration, cubicBezier, number, shadow, typography, fontFamily, fontWeight.
  • Aliases keep the tiers. A semantic token's $value is a reference such as {palette.pepper.600}, so tools can resolve or preserve the chain.
  • Extra metadata sits under $extensions["com.agent-toolkit"]: css (the custom property name), resolved (the final value in light) and themes, which holds each theme's override as themes.dark.$value plus its resolved value.
  • Light values are the defaults. Responsive overrides (columns, gutters, margins, header height and display sizes at 48rem and 62rem) and the reduced-motion and contrast overrides are not in the JSON; platforms apply their own equivalents.
"accent": {
  "$type": "color",
  "$value": "{palette.pepper.600}",
  "$extensions": {
    "com.agent-toolkit": {
      "css": "--color-accent",
      "themes": { "dark": { "$value": "{palette.pepper.300}" } }
    }
  }
}

To build platform constants, read $value for the light set and $extensions["com.agent-toolkit"].themes.dark.$value for the dark set, resolving {…} references through the same file. The Angular frontend does not consume the JSON at all: it links tokens/tokens.css and reads the custom properties by role.

Usage

  • Read colour by role (var(--color-fg-muted)), never by primitive (var(--palette-stone-700)) and never by hex (AGENTS.md).
  • Pick the role for what something is, not for how it looks in light: a pressed compare toggle is --color-accent-subtle, not "the pale pink".
  • Check every new screen in both themes before review; the mocks' t key and the docs toggle make that one keystroke.
  • Don't add @media (prefers-color-scheme) rules in components. If a component needs a different value in dark, it needs a semantic token.
  • Never dim, invert or filter photos, map tiles or posters in dark. They are the content.

Accessibility

  • Both themes pass every pair in contrast-pairs.json; check_contrast.py must exit 0 for light and dark before any colour change merges (L2-068.1).
  • Theme never carries meaning. Scores, stale flags, permit status, "Lowest" and errors read the same in both: words and numbers first, colour second.
  • Respect the person's choice: follow the operating system unless they choose otherwise, and keep their choice across visits.
  • Forced colours and increased contrast are honoured in both themes (see above).
