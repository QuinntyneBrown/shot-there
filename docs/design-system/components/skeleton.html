Skeleton

Skeletons draw the shape of what is coming (3:2 photos, studio names, admin rows, editor sections) in quiet stone, so a loading screen already looks like itself and nothing jumps when the content arrives.

Overview

A skeleton is a block of --color-bg-subtle with a slow shimmer, sized and placed like the content it stands in for. ShotThere uses skeletons wherever data arrives after the page:

  • Studio and spot lists: six .location-card--skeleton cards hold the grid while a filter or sort change takes longer than 300ms (L2-026.1). The first visit is server-rendered with the list in the HTML, so it never shows skeletons (L2-026.3).
  • Map: list rows in the map-list shape and one skeleton covering the map area.
  • Admin lists: table rows for studios, spots and guides; .admin-row--skeleton rows in the dashboard's re-verification list; skeleton stat tiles.
  • Editors: breadcrumb, title, status panel and section bars while a studio, spot or guide loads.

Choose something else when:

  • The wait is on an action, not on content (Delete studio, Sign in): the button's busy state, see spinner.
  • The amount is measurable (an image upload): a progress bar.
  • The load failed or returned nothing: an empty state, never a skeleton that shimmers forever.

Anatomy

  1. Media.skeleton--rect filling .location-card__media: the same 3:2 box and --radius-lg as the photo, so the grid does not shift.
  2. Title.skeleton--title: 1.5em high, 70% wide in a card, where the studio name goes.
  3. Text lines.skeleton--text: 0.9em high with 0.3em above and below, 50% wide in a card, for the neighbourhood line and the facts.

Variants

Shapes

Four shape modifiers on .skeleton. Width is set by the composite (card, row, tile) or by an inline width on the placeholder; height comes from the shape or the box it fills.

--title (40% by default), --text (the last line in a group is 60%), --rect for a field or photo box, --pill for a button.
HTML
<span class="skeleton skeleton--title"></span>
<span class="skeleton skeleton--text"></span>
<span class="skeleton skeleton--rect" style="height: var(--control-height-md);"></span>
<span class="skeleton skeleton--pill" style="width: 8rem; height: var(--control-height-md);"></span>

States

A skeleton is never interactive and never focusable, so hover, focus, active and disabled do not apply. Its only states are "loading" (present, region aria-busy="true") and "loaded" (removed, replaced by content in the same box). The matrix sets each loading shape beside what replaces it.

Both themes

  • Delayed: show skeletons only when a client-side refresh passes 300ms; quicker answers swap content in directly.
  • Loaded: replace the whole skeleton region at once, remove aria-busy, and update the status ("7 studios").
  • Failed: replace the skeletons with the error empty state and Try again (L2-026.2); Try again brings the skeletons back.

Responsive behaviour

Skeletons sit in the real layout containers, so they reflow exactly as the content will:

  • Card grid (.location-grid): one column on phones, two from 36rem, three from 62rem (two in the results column beside the filter sidebar, three again from 75rem).
  • Map: below 62rem only the list or the map is shown, whichever view is chosen; from 62rem both, each with its own skeleton.
  • Admin table (.table--stack): stacks into one card per row on phones; the skeleton cells stack with it.
  • Admin row: the Edit placeholder is 44px high on phones (--target-comfortable) and 32px from 48rem (--control-height-sm), matching the real button.
  • Editor: the status panel is above the sections on phones and a sticky 18rem right column from 62rem.
  • Fixed rem widths in the table never exceed their cell (max-width: 100%), so nothing scrolls sideways at 360px.

Theming

The block is a gradient from --color-bg-subtle through --color-bg-subtle-hover and back, moved across over --duration-loop. Both tokens are redefined for dark, so skeletons are a raised dark stone there with no change to the component. The card media keeps no photo background (background: none) so the rect's own shimmer shows.

Accessibility

Role and pattern

Skeletons are presentation. The container of placeholders is aria-hidden="true"; the region being loaded has aria-busy="true"; one role="status" message says what is loading ("Loading studios…", "Loading locations…", "Loading the dashboard", "Loading studio…"). This meets L2-026.1 and WCAG 4.1.3. No APG pattern applies.

Keyboard

KeyAction
TabSkips skeletons. Real controls around them (filters, Sort by, Filters, the admin search) stay usable while the list loads.

Focus

Focus stays where it was, usually on the filter or sort control that started the refresh. When content replaces the skeleton, focus does not jump into it.

Labelling

One message per region, not one per placeholder. In the editors, the breadcrumb's current item and the h1 carry visually hidden words ("Loading", "Loading studio") so headings navigation still works.

Contrast

"Loading studios…" status on the page
Real text that replaces a skeleton on a hovered row

Skeletons convey no information, so WCAG 1.4.11 does not apply to them; the status text does the telling. Keep them quiet stone, never coloured.

Motion

The shimmer is decorative and stops under prefers-reduced-motion: the blocks stay as flat stone. It is slow (1.4s), low contrast and covers no more than the region loading.

Touch

Nothing to touch. Skeletons never sit on top of a control and never block the filter or sort controls.

Content

  • Skeletons have no visible words; never put "Loading" text inside one.
  • The status message is "Loading" plus what is loading: "Loading studios…", "Loading spots…", "Loading locations…", "Loading the dashboard", "Loading studio…". Sentence case, ellipsis character.
  • When the content arrives, the same status element says what came: "7 studios", "5 studios".
