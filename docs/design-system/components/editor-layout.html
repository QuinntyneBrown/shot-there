Editor layout

The admin editors for studios, spots and guides share one layout: a status panel with Publish and Delete, beside a form split into collapsible sections, with the save bar pinned to the bottom of the screen. One column on phones; the status panel moves to a sticky right column from LG.

Overview

The editor layout is the admin's one long form. Only the owner sees it (/admin/studios/:id, /admin/spots/:id, /admin/guides/:id and their /new screens). It holds everything a review needs, so it is long; sections fold away so the owner can work on one part at a time without losing values (L2-054.6).

  • Status panel (.editor-aside): whether the location is a draft or published, its public address, and the publishing actions: Publish or Unpublish, and Delete.
  • Form (.editor-form): a stack of editor sections (.editor-section), each a native <details> whose <summary> holds the section's <h2>.
  • Repeating rows (.fee-row): a sunken row for each fee, included gear item or extra, with its own Remove button.
  • Save bar: the form layout's .form-actions--sticky with Save changes (or Create studio), Cancel and the live .save-status.

Sections by editor: the studio editor has Basics, Pricing and fees, Measured specifications, Gear, Logistics, Images, Rubric scores, Verdict, Disclosure and Episode video. The spot editor has Basics, Location, How to get there, Best light, Practical conditions, Permits, Best uses, Sample shots, Disclosure and Episode video. The guide editor has Basics and Entries.

Use something else for short forms (sign-in uses form layout on its own), for a confirmation (a dialog), and for anything public: visitors read reviews in the review layout, never in an editor. Image lists inside a section are the image manager.

Anatomy

  1. Status panel.editor-aside, an <aside> labelled by its "Status" heading. 1px --color-border-default edge, --radius-lg, --space-5 padding, --space-4 between parts; its buttons fill the width. Sticky from LG.
  2. Status details.editor-aside__meta, a <dl>: muted --text-body-sm terms over default-colour values. Long addresses break anywhere.
  3. Status actionsPublish (draft) or Unpublish (published) as a secondary button, then Delete as a ghost button in the danger text colour. No primary here: Save changes is the page's one primary.
  4. Section heading<summary><h2>: 52px (--control-height-lg) tall, the <h2> in --text-h4, a chevron drawn in CSS on the right that turns when open.
  5. Section body.editor-section__body: fields stacked --space-5 apart, padded --space-5 at the sides and --space-6 below. Values stay in the DOM when the section closes.
  6. Repeating row.fee-row: --color-bg-surface-sunken well with --radius-md; one column until the row itself is 34rem wide (a container query, so it also stacks beside the status panel between 62rem and 75rem), then name, amount, type and Remove on one line.
  7. Save bar.form-actions--sticky: pinned to the bottom of the viewport above the safe area, with Save changes, Cancel and the .save-status live region.

The layout does not change between editors; the status panel and the sections do. Pick the status panel by where the location is in its life (new, draft, published) and the section by what it holds.

The section is the only interactive part the layout owns. Its open state is the native open attribute; errors are data-invalid; focus is forced here with data-state="focus" on the summary so it can be reviewed without a keyboard. Fields, buttons and the image manager inside keep their own states.

Unsaved changes
  • Open rotates the chevron from pointing down (45°) to up (225°). Closing a section never clears or validates its fields.
  • Invalid: after a refused save the server's errors decide which sections open; each gets data-invalid, a danger-tinted edge and an error count in its summary (.editor-section__errors, "1 error"). The count, the error summary and the field messages carry the meaning; the edge alone does not (see accessibility).
  • Submitting never hides or disables fields; only the primary is busy. Uploading disables Save changes and says why in the save status (L2-057.6).
  • The position: static on the save bars in these tables is documentation only, so they do not stick to the viewport here.

Responsive behaviour

  • XS and SM (below 48rem): one column. The status panel comes first, above the form, then the sections full width (L2-054.6). Repeating rows stack name, amount, type and Remove. Every control is at least 44px tall; the save bar pins to the bottom with env(safe-area-inset-bottom) padding.
  • MD (48–62rem): still one column; repeating rows go onto one line (2fr / 1fr / 1.4fr / auto, aligned to the field bottoms). Two-field rows (.field-row) sit side by side from SM.
  • LG and up (62rem+): two columns, form then an 18rem status panel, 48px apart. The panel moves to the right with order: 2 and sticks 32px from the top, so Publish stays in reach while the form scrolls.
  • No horizontal scroll at any width: long addresses and file names break anywhere inside the panel and the image rows.
  • Known squeeze: just above 62rem the form column is about 35rem, and the one-line repeating row leaves Amount roughly 5rem wide, so the Amount column keeps at least 7rem (minmax(7rem, 1fr)) and "65.00" fits beside the $ addon.

Theming

The layout has no component tokens. It reads --color-border-default for the panel and section edges, --color-bg-surface for the sections, --color-bg-surface-sunken for repeating rows, --color-danger-border for invalid sections and --color-fg-muted for the status details. A theme changes those semantic tokens; nothing in .editor-* names a colour.

In light, sections are white on a white page, so the hairline edge is what groups them, and repeating rows are a step darker (stone-50). In dark, sections are the canvas colour (stone-950) with a stone-750 edge, and repeating rows are a step lighter (stone-900). The invalid edge goes from light red (sorrel-300) to deep red (sorrel-700).

Accessibility

Role and pattern

Each section is a native <details> and <summary>, the browser's built-in APG Disclosure: the summary is announced as a button with its expanded state, and no ARIA is added. The <h2> inside the summary keeps the section in the heading outline. Some screen readers announce only the summary's text and not the heading level; the name is the same either way. The status panel is an <aside> landmark named by its heading ("Status"); the form is named by a visually hidden <h2> ("Studio details").

Keyboard

KeyAction
Tab / Shift+TabMoves through the status panel, then each section heading and the fields of open sections, then the save bar. Fields in closed sections are skipped.
Enter, SpaceOn a section heading, opens or closes the section. Elsewhere, the control's own behaviour.
Enter in a text fieldSubmits the form (Save changes or Create studio).
Ctrl/⌘+FFind in page opens a closed section that holds the match, in browsers that support it.

Focus

The shared 2px ring appears on the summary (it keeps its --radius-lg corners). New studios focus Name. After a refused save, focus moves to the error summary (role="alert", tabindex="-1"); each of its links opens the section and focuses the field. After a price change, focus moves to Prices last verified. When an upload finishes, its alt text field takes focus (L2-057.1).

The status panel comes before the form in the DOM, so on phones it reads first and from LG it is still first in the tab order although it sits on the right. That order is deliberate: status, then content, then save.

Labelling

Section names are the summary headings. Remove buttons name their row with visually hidden text ("Remove Cleaning fee", "Remove Godox AD600 strobe"). The disabled Delete is described by its hint ("Unpublish before deleting."), and a disabled Save changes by the save status ("Wait for uploads to finish"). Field errors use aria-invalid="true" and aria-describedby (L2-069.2).

The data-invalid edge is below 3:1 and is not announced, so it is decorative. The summary also says how many errors the section holds in words (.editor-section__errors, in --color-danger-fg), which is part of the summary's accessible name (1.4.1). The server's errors still always open the section, and the error summary links every field.

Section and panel edges (--color-border-default) and the invalid edge (--color-danger-border) are decorative: grouping is also carried by the headings, and errors by text.

Motion

Only the chevron moves: it rotates over --duration-fast with --ease-standard, and reduced motion zeroes the duration. Sections open instantly; there is no height animation.

Touch

The whole 52px heading row is the target. Status panel buttons fill the panel width and are 44px tall; Remove buttons are 44px; Add fee and the image row buttons (.btn--sm, 36px) grow to 44px below 48rem (L2-065.3). Nothing depends on hover.

Content

  • Section headings are short nouns in sentence case and follow the order of the public review: "Basics", "Pricing and fees", "Measured specifications", "Gear", "Logistics", "Images", "Rubric scores", "Verdict", "Disclosure", "Episode video".
  • The panel heading is "Status". Terms are "Visibility" and "Public address" ("Public address once published" on a draft). Values say what visitors see: "Draft · not on the public site", "Published · on the public site", "Not saved yet".
  • Actions name the object: "Publish", "Unpublish", "Delete studio", "Delete spot", "Delete guide", "Create studio", "Save changes". When an action is blocked, say what to do: "Unpublish before deleting."
  • The save status is one short sentence: "Unsaved changes", "Saving…", "Saved 13 Oct 2026, 10:02 am", "Not saved. Fix the 6 things listed above.", "Wait for uploads to finish".
  • The error summary heading counts the problems: "Fix 6 things before saving". Each link is "Field: message", for example "Hourly rate: Enter an amount of 0 or more".
  • Mark optional fields "(optional)" and conditional ones with the condition: "Provided by (needed when discounted or comped)". Empty lists say what visitors will see: "Nothing yet. Visitors will see "Nothing costs extra"."
  • Measurements are metric in the editor ("Usable width (m)"); the public page adds imperial in brackets.

Drift found during extraction:

  • 75 inline style="font: var(--text-h4)" headings. None is a section summary heading: every <summary><h2> in the mocks is unstyled inline and takes --text-h4 from .editor-section > summary h2. The 75 are (a) 42 "Status" headings in the status panel (21 editor mocks, 5 admin-toast mocks and 16 dialog mocks), where no rule styled .editor-aside headings, so the inline style filled a real gap; and (b) 33 section names in the editor stand-ins behind 16 dialog mocks, drawn as <div class="editor-section"><div class="editor-section__body" style="padding-top: var(--space-5)"><h2 style="…"> instead of <details><summary><h2>, which is drift. This page uses real sections, and .editor-aside > h2 { font: var(--text-h4); } now styles the status heading, so the inline style can go.
  • Delete colour is inline. "Delete studio" / "Delete spot" / "Delete guide" use style="color: var(--color-danger-fg)" in 14 editor mocks, but the disabled Delete in spot-editor/published and guide-editor/published drops it. .btn--ghost-danger now colours every one, disabled or not; the examples here use it.
  • Publish and Unpublish are links (<a class="btn" href="…dialogs/…">) because the mocks navigate between files; in the product they are <button type="button" aria-haspopup="dialog">. The page shows buttons.
  • Invalid sections are colour-only. --color-danger-border is about 2.4:1 on the light section and 1.9:1 in dark, and nothing in the mocks' summaries says "error". The edge is documented as decorative with errors always open, and .editor-section__errors adds a count in words ("1 error"); the mocks do not show it yet.
  • Error summary headings disagree: "Fix 6 things before saving" (studio), "Fix 4 problems before saving" (spot), "This guide can't be published yet" (guide invalid). The page uses "Fix N things before saving".
  • Missing-fields dialog: every link points to the editor without a field fragment, although L2-056.3 asks for links that focus the field, and the only button is "OK". The page documents link-to-field; the button should be a verb ("Close").
  • Inline layout in states: the loading mocks rebuild the summary row's size inline on div.editor-section, and price-changed draws its warning well inline on .field. .editor-section--skeleton and .field--warning now do both; the examples here use them.
  • Repeating row at LG: with the 18rem status panel beside it, the .fee-row Amount column (1fr) shrank to about 5rem between 62rem and 75rem. Fixed: the row now lays out by its own width (a container query on its parent), so it stays stacked there, and the amount column is minmax(7rem, 1fr) once it goes four-up.
