Email signup

The email signup is the one form visitors fill in: an email address and a Subscribe button that gets them one email per new review. It sits in the home page hero and in the footer of every public page, and confirms inline without leaving the page.

Overview

ShotThere has no visitor accounts. The signup is how a visitor follows the site: they give an email address and hear when a new studio or spot review goes up (L2-039). It is a small, self-contained form built from the form field, text field, button and alert; this page documents how they combine and behave.

  • Hero placement on the home page has the primary (ink) Subscribe: it is the page's one primary action.
  • Footer placement repeats on every public page with a secondary Subscribe, so it never competes with the page's own primary action.
  • Never put the signup in a dialog, a sheet or a toast, and never ask for anything besides the email address. Admin forms are not signups; they use the form layout.

The browser checks the address before anything is sent; the server checks it again, stores it lowercase with the time and source page, ignores the honeypot and rate-limits by client (L2-040). An address that is already subscribed gets the same confirmation as a new one, so the form never reveals who is on the list (L2-039.4).

Anatomy

  1. Title.signup__title: a real heading in --text-h4; it names the form through aria-labelledby.
  2. PromiseOne plain <p> saying how often and what is sent.
  3. Email fieldA .field with a visible "Email address" label and a 44px .input type="email".
  4. Row.signup__row: field and button stacked at XS, side by side from SM.
  5. SubscribePrimary in the hero, secondary in the footer; type="submit".
  6. Honeypot.signup__trap: an off-screen "website" field, out of the tab order and hidden from assistive technology. Not visible.

Below the row, the form can hold one message at a time: the field error (.field__error), a warning alert for rate limiting or a danger alert for a failed request. On success the whole form is replaced by .signup__done.

Variants

Same fields, same behaviour; the placement sets the emphasis and the copy.

Inside .site-footer the form flexes from 20rem (.site-footer .signup), the Subscribe button is secondary, and the footer's muted link styles are undone so the button keeps its own colour and 44px height.

Sizes

One size. The input and Subscribe are both --control-height-md (44px) everywhere; the form is capped at 32rem and fills its column below that.

Responsive behaviour

  • XS (below 36rem): the field and Subscribe stack and both are full width (L2-039.5). Messages sit under the button.
  • SM and up (36rem): one row; the field grows (flex: 1) and Subscribe keeps its natural width, aligned to the bottom of the input rather than the top of the label.
  • The form is capped at 32rem so the input never becomes a page-wide bar on desktop.
  • Footer: the form takes a flexible column from 20rem beside the brand and links, and wraps under the brand when the footer is narrower.
  • The honeypot is positioned off-screen with left: -100vw inside a 1px box, so it never causes horizontal scroll.

Theming

The signup has no component tokens. It reads the field tokens (--field-bg, --field-border, --field-fg), the button tokens (--btn-bg, --btn-fg, --btn-border) and the alert tokens, so a theme or re-skin of those parts changes the signup with them. Its own colours are --color-fg-default for the title and confirmation and --color-success-icon for the tick.

The footer placement needs one override: .site-footer a and .site-footer text are muted, so .site-footer .signup .btn sets the label back to --btn-fg and keeps it on hover. In dark the primary Subscribe flips to light stone with near-black text, the input sits on the stone 950 surface and is defined by its neutral stone 500 border, and the success tick lightens to success green 300.

Accessibility

Role and pattern

A native <form> named by its heading (aria-labelledby), so it is a form landmark ("Get new reviews by email, form"). A native <input type="email"> and a native submit <button>. novalidate turns off browser bubbles; the page validates and shows its own message. The honeypot wrapper is aria-hidden="true" and its input has tabindex="-1", so neither keyboard nor screen reader users reach it.

Keyboard

KeyAction
Tab / Shift+TabEmail field, then Subscribe. The honeypot is skipped.
Enter in the fieldSubmits the form, like pressing Subscribe.
Enter, Space on SubscribeSubmits. While busy the button ignores further presses.

Focus

On an invalid submit, focus moves to the email field, whose error is then read with it. On success, focus would be lost with the removed form, so it moves to the confirmation (give the wrapper tabindex="-1" and focus it), which the status region also announces. On a server error or rate limit, focus stays on Subscribe so the visitor can retry at once. Never use autofocus on page load.

Labelling

"Email address" is a visible <label>; there is no placeholder. The input sets autocomplete="email" and inputmode="email" (WCAG 1.3.5). Errors use aria-invalid="true" and aria-describedby pointing at the .field__error (L2-069.2). The confirmation is in role="status" with aria-live="polite"; rate-limit and server errors are role="alert". The busy button keeps its name "Subscribe" with aria-busy="true".

The success tick (--color-success-icon on the page) repeats what the text says, so the confirmation does not depend on it; its 3:1 pair against --color-bg-canvas is not yet in contrast-pairs.json and is listed as a need.

Motion

Only the busy spinner moves; it keeps turning under reduced motion because it reports status. The swap from form to confirmation is instant, with no animation.

Touch

The input and Subscribe are 44px tall at every width, and full width on phones (L2-065.1). inputmode="email" brings up the email keyboard. The input text is 16px, so iOS does not zoom on focus.

Content

  • Title says what arrives: "Get new reviews by email" (hero), "New reviews by email" (footer).
  • Promise says how often and what is not sent: "One short email per new review. No ads, no sponsors." / "One email when a new studio or spot goes up. Unsubscribe any time."
  • Button is always "Subscribe". Not "Sign up" (there are no accounts) and not "Submit".
  • Errors say how to fix it: "Enter your email address", "Enter a valid email address, like name@example.com".
  • Rate limit: "Too many tries." with "Wait a minute, then try again." Server error: "We couldn't subscribe you just now." with "Your email is still here — try again."
  • Confirmation repeats the address so a typo is visible: "You're subscribed. We'll email maya.chen@example.com when a new review goes up." It never says "already subscribed".
  • The honeypot label "Leave this field empty" is only for the rare bot that reads labels; it is never shown.

Drift found during extraction:

  • Every mock's hero and footer Subscribe carries an inline style="align-self: flex-end;" to line the button up with the input instead of the label. The examples here keep it so they render as the mocks do; the fix is a rule in .signup__row (proposed), after which the inline style goes.
  • pages/home/invalid puts autofocus on the invalid input to show where focus lands. On a real page focus moves there after submit, not on load.
  • pages/home/success replaces the form without moving focus. Documented: move focus to the confirmation.
  • The "not-an-email" message exists only as a mock note (README assumption 13); no mock renders it. Shown here.
