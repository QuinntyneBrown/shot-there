Inline message

Inline messages are the one-line notes that sit right where the problem is: help under a field, the error once the server refuses a value, the warning after a price edit, an upload that failed, and the save status beside Save changes in the editors.

Overview

Use an inline message when the note belongs to one field, one image or one form's save button. When it is about a whole page or section, use an alert; when it confirms an action that just finished, use a toast.

  • Help (.field__help): always visible, says what to enter or what happens: "Visitors see a warning after 183 days."
  • Error (.field__error): appears after a refused submit, says how to fix it, and pairs with aria-invalid="true" on the control. Also used without a field for an upload that failed or a list that needs an entry.
  • Warning (.field__warning): the value is allowed but needs a second look. Only one in ShotThere: after a price edit, "You changed a price. Confirm the date you verified it." (L2-042.2).
  • Save status (.save-status): the editor's state beside Save changes in the sticky form actions: "Unsaved changes", "Saving…", "Saved 13 Oct 2026, 10:05 am".

The server stays the authority: the browser may show these messages early, but every rule is checked again on save.

Anatomy

  1. Invalid controlaria-invalid="true" gives the danger border; aria-describedby lists the error first, then the help.
  2. GlyphA CSS ::before with empty alternative text: "⚠" for errors, a ringed "!" for warnings. Shape plus colour, never colour alone.
  3. Message--text-body-sm in --color-danger-fg (or --color-warning-fg); one sentence, wraps anywhere.
  4. Help.field__help in --color-fg-muted; stays under the message so the guidance is not lost.

Responsive behaviour

  • Messages take the field's width and wrap; long file names such as "studio-floorplan.svg" break anywhere instead of widening the form at 320px.
  • The save status sits after Cancel in .form-actions--sticky, which stays at the bottom of the viewport above the safe-area inset; on a phone it wraps to its own line under the buttons.
  • In two-column field rows (Hourly rate, Minimum booking) each message stays under its own field.

Theming

Messages read the status foregrounds --color-danger-fg, --color-warning-fg and --color-success-fg, and --color-fg-muted for help and neutral status. The dark theme lightens each foreground so it holds 4.5:1 on the dark canvas, surface and dialog. The glyph uses currentColor, so it follows the message.

Accessibility

Role and pattern

Help, errors and warnings are plain text tied to the control with aria-describedby (WCAG 3.3.1 Error Identification, 3.3.3 Error Suggestion). Errors that come from a submit are announced through the form summary (role="alert", focused), not one by one. Messages that appear without a submit, like a failed upload, use role="alert". The save status is a polite live region, role="status", rendered with the page so changes are announced (4.1.3 Status Messages). The glyph's content: "⚠" / "" gives it empty alternative text.

After a refused save focus goes to the form summary; the invalid field keeps its danger border under the focus ring.

Labelling

List the message before the help in aria-describedby ("bookingUrl-error booking-help") so the fix is heard first. The image-row error names the file ("gallery-04.jpg didn't upload"), so it makes sense out of context.

Motion

None. Messages appear and disappear without animation.

Touch

No targets of their own; Retry and Remove next to an upload error are 44px on phones.

Content

  • Errors say what to do, in the imperative, with no full stop: "Enter a whole number from 1 to 5", "Describe this image", "Enter who provided the session".
  • Name the limit, not the rule number: "The limit is 20 MB.", "Enter a latitude from -90 to 90".
  • Never blame: "isn't a supported image", not "invalid file". No "Error:" prefix; the glyph and colour already say it.
  • Help is a full sentence that adds something the label doesn't: what visitors see, where to find the value.
  • Save status is short and specific; times use "10:05 am" and dates "13 Oct 2026".
  • Email errors follow the README wording: "Enter your email address", "Enter a valid email address, like name@example.com".

Drift found during extraction:

  • studio-editor/price-changed tints the warning field with an inline style (padding, radius, --color-warning-bg). .field--warning now does it, and the muted help and body text on that tint are checked pairs in contrast-pairs.json; the warning example above uses the class.
  • No mock uses .save-status--saved or --error: "Saved…" and "Not saved…" render neutral. Documented with the modifiers.
  • The refused-save status reads three ways: "Not saved. Fix the 6 things listed above." (studio), "Not saved" (spot), "Not published" (guide); studio-editor/new leaves the status empty where the other editors say "Not saved yet". Documented with the studio wording.
  • aria-describedby order varies: error first in studio-editor/invalid, help first in spot-editor/invalid (video, permit source). Documented error first.
