Form field

The wrapper around every control: a visible label, the control, one message slot for an error or a warning, then help, 4px apart. Sign-in, the studio, spot and guide editors, the filters and the email signup all build their fields this way.

Overview

Every text field, textarea and select sits in a .field. The field gives the control its name and its descriptions, and keeps them in the same order everywhere: the owner's sign-in, the editor sections, the filters dialog and sidebar, the admin list search and the email signup.

  • Label is always visible, above the control: "Email", "Hourly rate", "Prices last verified", "Search by name or neighbourhood". Placeholders are never labels; no ShotThere mock uses one.
  • Optional marker (.optional) goes on the few fields that can stay empty: "Backdrops (optional)", "Load-in note (optional)", "YouTube link or video ID (optional)". A field needed only in some cases says when: "Provided by (needed when discounted or comped)".
  • Message slot holds at most one message, directly under the control: an error (.field__error, danger red, blocks the save: "Enter an amount of 0 or more") or a warning (.field__warning, warning amber, asks for attention but doesn't block: "You changed a price. Confirm the date you verified it.").
  • Help (.field__help) says what a good answer is or what happens with it: "The studio's own booking page. Opens in a new tab for visitors."
  • Inline field (.field--inline) puts a short label beside its control, for the "Sort by" select above the studio list.
  • Counter (.field__counter) is in the stylesheet but no ShotThere mock uses it, because no field has a character limit yet (see Variants).

Groups of checkboxes or radios use a <fieldset> and <legend> instead (see checkbox and radio group); in the filters each group is a filter group. Layout across fields (rows, sections, sticky actions) is form layout; validation timing and the error summary are the forms pattern.

Anatomy

  1. Label<label class="field__label" for>; --text-label in --color-fg-default. Wraps, never truncates.
  2. Optional marker.optional inside the label: "(optional)" or the condition, regular weight, --color-fg-subtle. Part of the accessible name.
  3. ControlInput, textarea, select or input group, full width, 4px below the label.
  4. Message slotOne .field__error or .field__warning, 4px below the control and before the help. A CSS icon plus words; never colour alone.
  5. Help.field__help, --text-body-sm in --color-fg-muted. Stays in place when an error appears.

This is the spot editor's video field after a failed save (pages/spot-editor/invalid).

Spacing

  • Between the parts of one field: --space-1 (4px), from .field's gap. Don't add margins to the help or the message.
  • Between fields: --space-5 (20px) inside an editor section (.editor-section__body), --space-4 (16px) on sign-in (.stack) and between the two fields of a .field-row, --space-3 (12px) under a field inside a .filter-group.
  • An inline field puts --space-2 (8px) between "Sort by" and the select.

Inline (.field--inline)

The sort control beside the result count and Filters on pages/studios/default (L2-023). The row wraps, so on a narrow phone the select drops under its label instead of overflowing. Use it only for a short label and one control, never for a field that can show an error.

<div class="field field--inline">
  <label class="field__label" for="sort">Sort by</label>
  <select class="select" id="sort" name="sort">

    <option value="cost">All-in cost, low to high</option>

Sizes

The field itself has one size: label --text-label, help and messages --text-body-sm, counter --text-caption. It follows its control's size without changing its own text or spacing: sign-in uses .input--lg (52px), everything else the medium control (44px).

The sign-in email (large control) and the studio editor's neighbourhood (medium). The label and the 4px gap are the same.

States

The field shows its control's state and adds the message. Hover and focus are forced on the control with data-state; invalid, disabled and read-only use aria-invalid, disabled and readonly. A field has no active state of its own.

  • Invalid appears after a submit, with the error summary ("Fix 6 things before saving", "Fix 2 things to sign in"), and never while someone is still typing a first attempt. The value is kept, even when wrong ("-5", "corktowngarage").
  • Warning appears as soon as the cause is known (here, the moment a price changes) and never blocks on its own. It is warning amber with a ringed "!", so it can't be mistaken for an error.
  • Error and warning together: show only the error; the warning returns once the error is fixed.
  • Disabled is for a field that can't apply yet, and the label says when it will: "Provided by" stays disabled until Discounted or Comped is chosen.
  • Read-only: while sign-in submits, both inputs go readonly (not disabled), so the values stay readable and focus isn't lost (pages/sign-in/submitting).

Responsive behaviour

  • A field is always the full width of its column. The editor form sits in the editor layout's main column; sign-in caps at 28rem (.auth); the signup caps at 32rem.
  • From 36rem, .field-row puts two short fields side by side (Hourly rate and Minimum booking; Usable width and Usable depth). Below 36rem they stack.
  • In the email signup, the field and Subscribe stack full width below 36rem and share a row from 36rem (L2-039.5).
  • .field--inline wraps: at 320px "Sort by" stays on its line and the select moves under it rather than pushing the page sideways.
  • Labels, help and messages wrap; nothing truncates. Long words such as a pasted booking link break with overflow-wrap: anywhere.

Theming

The field reads semantic tokens only: --color-fg-default (label), --color-fg-subtle (optional marker, counter), --color-fg-muted (help), --color-danger-fg (error, over-limit counter) and --color-warning-fg (warning). The control's own tokens (--field-bg, --field-border, --field-fg) live on the text field.

In dark, the canvas and the dialog surface both darken and the message colours lighten to their 300 steps (danger red and warning amber), so each text pair keeps 4.5:1 on the page, in the filters sheet and in dialogs. prefers-contrast: more lifts muted and subtle text a step without any change here.

Accessibility

Role and pattern

Native labelling: a <label for> pointing at the control's id, and aria-describedby listing the message, then the help, in the order they appear. Errors set aria-invalid="true" on the control (L2-069.2). Required fields use required; there are no asterisks. See the W3C forms tutorial and WCAG 3.3.1.

Keyboard

KeyAction
Tab / Shift+TabMoves between controls. The label, help and messages are not tab stops.
Click or tap the labelFocuses the control, a bigger target than the control alone.
Enter on an error-summary linkMoves focus to this field's control, which then reads its label, error and help. The section holding it is already open.

Focus

The ring sits on the control, not the field. After a failed submit, focus goes to the error summary first, so the number of problems is heard before the first one (pages/sign-in/invalid). In the filters dialog the invalid maximum takes focus, because there is no summary there (dialogs/studio-filters/invalid).

Labelling

The label is a sibling of the control, not its parent. A <label class="field"> that wraps the help and the error puts all of that text into the accessible name, so the field would be read as "Booking link The studio's own booking page. Opens in a new tab for visitors." and then the same help again as its description. "(optional)" and the condition stay inside the label on purpose. When several fields share a visible label, as each guide entry's "Editor's note", a visually hidden suffix makes each name unique: "Editor's note for Kensington Window Room". The error's icon is generated by CSS with empty alternative text, so it is not read aloud.

Motion

Messages appear without animation, so the layout shift is immediate and short. The control's edge transitions over --duration-fast; reduced motion zeroes it.

Touch

The label is part of the target (tapping it focuses the control), and every control is at least 44px tall at phone widths (L2-065.3). Help and messages are not interactive.

Content

  • Labels are short nouns in sentence case, without colons: "Hourly rate", "Usable width (m)", "Prices last verified", "Who should skip it".
  • A unit belongs in the label or in an addon, never typed into the value: "Minimum booking (hours)", "Focal length (mm)", "$" before the rate.
  • Help gives the rule, an example or the consequence: "Write "None" rather than leaving it empty.", "Lowercase words and hyphens. Changing it after publishing redirects the old address."
  • Errors say what to do and name the limit, and the summary repeats them word for word after the field's name: "Hourly rate: Enter an amount of 0 or more". Never "Invalid input".
  • Warnings say what changed and what to do, without blame: "You changed a price. Confirm the date you verified it."
  • Sign-in errors never say which of the two fields was wrong once both are filled: "Email or password is incorrect" is an alert above the form, not a field error (L2-049.2).
